하이라이트

BlindSpot 인식

"솔직한 모름"이 "모호한 추측"보다 중요합니다. 그래프 경계를 명시하여 에이전트가 의존성이 없다고 착각하는 것을 방지합니다.

상태 비저장 & mmap

상주 데몬의 부담 제거. Rust + rkyv 기반으로 각 쿼리는 그래프를 mmap 후 종료 — 실측 65–76 ms(프로세스 기동 비용 포함). 고빈도 병렬 에이전트 쿼리를 위한 설계.

아키텍처 레이더

단순한 AST를 넘어 고급 아키텍처 제약 조건 인식. Saga, EventTopic, API 계약 패턴을 감지하여 위험을 조기에 드러냅니다.

grep보다 7.5× 적은 토큰

ecp impact의 3홉 호출 체인은 약 111 토큰. 동등한 grep 출력은 약 830 토큰이며 이후 파일 읽기는 별도입니다. 본 저장소에서 실측.

리팩터링 안전한 엣지 시맨틱

is_test / is_direct 플래그로 테스트 호출자를 제외하고 동적 디스패치를 드러냅니다. impact --literal은 파일 읽기와 쓰기를 구분 — grep은 구조적으로 불가능.

디스패치 순간에 개입

PreToolUse 트립와이어가 '코드 탐색' 에이전트 디스패치를 그래프 쿼리 한 번으로 전환 — 정적 가이드가 모델의 주의에서 사라진 바로 그 순간에 작동.

  • Cairo: use X as Y + type X = Y
  • Move: use ... as alias clause (module + braced-member forms)
  • Zig: const X = @import(...) / const X = Identifier (numeric/string/bool literal RHS filtered via parser-side priority promotion)
  • Crystal: alias X = Y
  • Nim: type X = Y with object/distinct/ref-type/tuple-object shapes filtered out (those stay Class)
  • Vyper: from X import Y as Z / import X as Y (source-line scan — grammar can't AST-parse the as clause)
  • Solidity: using L for T directives + type C is uint256 user-defined value types
  • HCL: locals { } block attributes (output blocks remain Const)
  • SQL: top-level CREATE VIEW v AS … (column aliases SELECT x AS y not captured)
  • Verilog: SystemVerilog typedef declarations
  • C: typedef + #define / preproc_function_def + extern declarations (include-guard macros filtered; classified as Alias/Constant/Macro/Flag)
  • Swift: typealias declarations + @objc(extName) rename attributes

Ctor — on Go and Rust

Neither language has a language-level constructor. Go uses factory functions (NewFoo()) and Rust uses associated functions (Foo::new()) as idiomatic substitutes, but the cross-language Ctor extractor only emits NodeKind::Constructor for languages with a reserved ctor name (__init__, initialize, __construct, constructor, Class::Class).

Entry — on JavaScript and Ruby

Absence of a language-level main convention (per entry_points.rs coverage table). Entry points still surface for these languages via route handlers and framework decorators — just not via a main() symbol.

Rename n/a on markup/config rows

Markdown, GitHub Actions, Docker Compose, Dockerfile, and YAML carry keys / literal strings, not re-bindable code identifiers — ecp rename would have nothing to rewrite.

개발 Q&A

During agent communication, LLMs easily fall into a closed-world assumption. To an LLM, anything unknown might be treated as non-existent. Therefore, making the LLM aware that it 'does not know' is crucial to prevent hallucinations.

Knowing what is 'unknown' allows the LLM to dig deeper and find actual answers, rather than having the tool mask the unknown, causing the LLM to believe the unknown information simply doesn't exist.

Thus, the value of BlindSpot is not to complete the graph, but to honestly reveal the graph's boundaries. Without marking BlindSpots, human engineers might suspect a hidden trap; but an Agent might directly interpret 'no edge' as 'no dependency'. This is extremely dangerous for large systems.

In fact, all advanced Agentic Developers or Departments have already started adopting this mechanism gradually, though mostly implemented at the workflow level. Building workflows is often complex and massive, but through a simple peer design, code agents can instantly share their current development info with each other, avoiding duplicate work or introducing conflicts between their parallel efforts.

Today we have the sub-agent development model, but this mechanism is merely an extension of a single session. Sub-agents just complete tasks handed down by the main agent.

Through ecp peers, what I hope to achieve is a massive group of main agents completing grander plans by mutually exchanging information, rather than just communicating through document records. Such a design can advance everyone's progress in real-time and accomplish larger-scale design planning.

The stateless concept of mmap and rkyv depends on performance and stability.

Once a server boots up, it can hold state, but to maintain that state, we need more complex processes and code to ensure the stability of all states. Every interaction with the server is a cost; necessary caching also costs memory. Numerous constraints result in poor performance.

Through mmap, all agents share the underlying common resource. They do not need to own state; instead, they work via near-instant queries against static data. In practice, building a graph of 16k files and 300k nodes takes only 2 to 3 seconds, producing a graph.bin that is less than 70 MB. Because of the shared mmap design, various CLI queries generally return within 100 ms.

This model is vital for Agents because Agent systems inherently feature high concurrency, short lifespans, frequent restarts, and cross-session operations. Statelessness isn't just for speed; it's to minimize failure modes.

Yes. The greater challenge for AI Agents in software development is shifting from 'can it write a function correctly' to 'can it avoid breaking existing architectural constraints in a large system'.

The correctness of a single function can be solved by types, tests, linting, and local context; but real system risks often hide in constraints that cross files, services, languages, and time.

LLMs can deduce things themselves via basic graph queries, but that isn't a stable solution. The problem isn't that LLMs can't reason, but that making them rediscover architectural patterns from low-level nodes and edges every time is costly, yields inconsistent results, and easily misses 'negative space'. Therefore, ECP has built-in pattern detection like Saga and EventTopic, elevating high-risk, common, structurable architectural knowledge into first-class signals ahead of time. More accurately, it acts as an Agent's architecture radar: laying out high-confidence constraints and implicit couplings clearly before code is modified.

GitNexus is not my project; it's the origin of my project. I encountered issues while using GitNexus: performance, multiple daemon servers, and several architectural bottlenecks, so I independently developed the Rust architecture.

The first breaking point was when resident state began to restrict Agent workflows. When multiple Agents, worktrees, repos, and branches query simultaneously, the daemon model easily becomes a hidden coordination problem. The second breaking point was a shift in expected query frequency. I wanted something closer to an Agent's L1 / L2 cache: querying in milliseconds before every file edit, rename, review, or impact analysis. At this frequency, the costs of a Node.js daemon became glaring.

Thus, the core thesis of the Rust stateless architecture is: bake the graph into a fixed-format graph.bin so that every CLI / MCP query directly mmaps it, requiring no warm-up, no daemon state, and no trust in a long-lived process.

Initially, I didn't want to reinvent the merge queue. I just wanted to feed ecp impact signals into existing queues, so I created ecp dev pr-analyze to automatically label workflows with area, risk, and cross-pr-conflict.

But after dogfooding, I found that the real value wasn't the queue itself, but 'using the graph to judge if PRs can safely run in parallel'. Even if two PRs touch different files, if one modifies a symbol within the other's blast radius, it's considered a semantic conflict. Conversely, if two PRs are in unrelated areas and their impact sets don't intersect, they can be labeled as low-risk, no cross-PR conflict, and handed to the workflow for more aggressive merging.

What this feature truly saves isn't single CI execution time, but reducing the cycle of PRs drifting from each other, leading to endless rebases and CI reruns. ECP's vision here is: elevating the merge queue from 'time-based queuing' to 'risk-based scheduling'.

The rhythm traditional human teams use to manage changes isn't necessarily wrong, but the overall process system should be more automated to avoid hindering development.

Agent coding speed is very fast now, but the obstacle is actually human fear and worry. Fear of code conflicting, fear of the LLM breaking B while changing A, fear of various code errors—these fears have become the biggest problem hindering development.

As projects developed by everyone, every team, and every company grow exponentially in the future, similar tools will become more critical, and performance will be a fatal key. How to let the LLM understand the current architecture faster, rather than relying on long-term memory context processing, becomes relatively important. We should let the LLM understand the architecture through the source code itself, not through text records of the architecture, because only the source code is the only truth.

In the AI Agent era, 'flowcharts' will actually become the most important form of documentation, because what humans need to manage are processes and architectural design. Through charts, we can quickly see each design, but how the code is generated, how tools verify it, and how Agents consume it will gradually become less important.

However, underlying core designs should still be recorded—for example, how to utilize cache, whether there should be a warm-up, what the client timeout should be, etc. These design documents are still important, just abstracted to a broader scope. Accurately speaking, all documentation will move towards higher-dimensional design.

Just as we no longer delve into how machine code is compiled or run when writing programs today. Egent Code Plexus itself is merely a transitional product adapting to current trends.

ECP should focus on being a blazing fast, trustworthy, source-code-grounded structure awareness layer.

This project will not, and does not need to, become another Codex, Claude Code, or OpenClaw. Rather, it is a tool feature that these code agent workflow frameworks can opt to use when they need to understand code. It is simply a grep / read tool exclusively for LLMs.

Traditional tools answer 'Where is this string?' and 'What are the contents of this file?', whereas ECP answers: 'What is this symbol?', 'Who calls it?', 'What upstream/downstream does it affect?', and 'What is the structural risk of this diff?'. ECP's core is not making decisions for the Agent, but providing the structural facts the Agent must know before making a decision.

The most important product interface is the CLI.

MCP involves more maintenance trouble, but because not every code agent framework can natively call the CLI, a dual architecture was adopted, offering MCP to guide the use of CLI calls. However, a better approach would be to embed the tool directly as a CLI tool, just like read. This is a massive help for improving performance and reducing tokens.

The advantages of the CLI are that it is simple, low maintenance, easy to test, easy to drop into CI, and has no server lifecycle, tool registration, schema compatibility, or session state issues. MCP's value is as a compatibility layer, not the core abstraction.

Before these designs are learned by LLMs, skills are needed to regulate and guide them. Just like before humanity learned to use fire, they didn't know its uses. But as this knowledge becomes widely applied, most people won't need to take courses on how to use fire.

Currently, we still need skills to regulate and guide, unless one day LLMs have this related knowledge built-in. But I hope skills are not used to restrict how LLMs use tools, but rather as a guide. Tools should describe their functions, while how to use them is guided by the skill, which can also be adjusted according to personal needs. The ultimate hope, of course, is that LLMs understand autonomously and apply them more broadly.

'All actions should start from verifiable structural facts, not from context hallucinations.'

Any preceding text can become a hallucination; only immediately confirmed situations are verifiable. This is exactly why the peer feature was designed: to achieve semi-real-time interaction via hooks/peers to avoid development conflicts from arising.
