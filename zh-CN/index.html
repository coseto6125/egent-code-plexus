Egent Code Plexus v0.9.2

Built for agents, not IDEs.

专为 AI Agent 设计的代码结构感知与架构雷达

Egent Code Plexus（ecp）是面向 AI coding agent 的命令行代码结构图谱。它把仓库索引成符号图，直接回答结构问题：哪些函数调用了它、这次改动会破坏什么、这个服务触及哪些 HTTP 路由与数据库表，覆盖 31 种语言，毫秒级响应，无需常驻进程。图看不到的地方会用 BlindSpot 明说，而不是返回一个看起来像「不存在」的空结果。

curl -sSfL https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.sh | sh
iwr https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.ps1 -UseBasicParsing | iex
cargo install --git https://github.com/coseto6125/egent-code-plexus egent-code-plexus --bin ecp --locked

快速开始

1. 启动 AI Onboarding Wizard

在您的 AI Agent（如 Claude Code）中贴上专属指令，唤醒交互式向导，为您完成环境检测与自动安装。

/chat Fetch https://raw.githubusercontent.com/coseto6125/egent-code-plexus/main/docs/skills/ecp-onboard/SKILL.md and follow it as my onboarding wizard

2. 建立索引（非必要 / Auto-Index）

ECP 内置 auto-ensure 机制，在您第一次查询时会自动建立图谱，因此手动执行索引通常是非必要的。

ecp admin index --repo <path>

3. 多项目群组（Group）

如果是微服务或前后端分离架构，可建立群组以实现跨 Repo 查询。

ecp admin group add <group_name> <path>

4. 确认 MCP 集成（Verify）

Onboarding 向导会自动为 IDE 写入 MCP 设置。完成后，您可通过 CLI 确认已暴露给 Agent 的工具清单。

ecp admin mcp tools

技术亮点

BlindSpot Awareness

“诚实的不知道”比“模糊的猜测”重要。明确标记图谱边界，防止 Agent 把“没有边”误认为“没有依赖”，从根本上解决 LLM 的闭世界幻觉。

Stateless & mmap

抛弃常驻 daemon 的负担。基于 Rust + rkyv，每次查询直接 mmap 图文件后退出——实测 65–76 ms（含进程启动成本）。为高频并发的 Agent 查询而生。

Architecture Radar

从简单的 AST 关联，升级到高级架构约束感知。内置 Saga 补偿事务、EventTopic 发布订阅、以及跨服务 API 契约的模式检测，提前揭露隐性风险。

比 grep 省 7.5× tokens

ecp impact 返回的 3-hop 调用链约 111 tokens；等效 grep 输出约 830 tokens——这还没算 grep 之后必须补读的文件。实测于本项目。

重构安全的边语义

is_test / is_direct 标志可排除测试调用者、识别动态派发；impact --literal 区分文件读与写——grep 在结构上做不到的区别。

在 dispatch 当下拦截

PreToolUse tripwire 把「探索整个 codebase」的 agent 派发改导向一次图查询——作用在静态指引早已从模型注意力中流失的那个时刻。

31 种语言，一次遍历

服务代码、IaC、字符串内 SQL 全部解析进同一张图（QueriesTable 边）——混合技术栈 repo 在单语言工具失明之处，图谱仍然亮着。

Imports

  • Bash: source / .
  • Lua: require + binding alias
  • Dockerfile: FROM <base>
  • GitHub Actions: uses: directives — public tag/SHA refs, local composites, reusable workflows, cross-repo workflows
Named

  • Bash: alias command
  • Lua: local M = require(...) and dotted-path bindings (plain literal RHS filtered)
  • Cairo: use X as Y + type X = Y
  • Move: use ... as alias clause (module + braced-member forms)
  • Zig: const X = @import(...) / const X = Identifier (numeric/string/bool literal RHS filtered via parser-side priority promotion)
  • Crystal: alias X = Y
  • Nim: type X = Y with object/distinct/ref-type/tuple-object shapes filtered out (those stay Class)
  • Vyper: from X import Y as Z / import X as Y (source-line scan — grammar can't AST-parse the as clause)
  • Solidity: using L for T directives + type C is uint256 user-defined value types
  • HCL: locals { } block attributes (output blocks remain Const)
  • SQL: top-level CREATE VIEW v AS … (column aliases SELECT x AS y not captured)
  • Verilog: SystemVerilog typedef declarations
  • C: typedef + #define / preproc_function_def + extern declarations (include-guard macros filtered; classified as Alias/Constant/Macro/Flag)
  • Swift: typealias declarations + @objc(extName) rename attributes
  • Ruby: alias keyword + alias_method + constant assignment (MyConst = Other::Constant) + def_delegator / def_delegators / delegate (with Forwardable mixin detection; cross-file include Foo propagation resolved via resolver Tier 2.75 HeritageScoped)
  • GitHub Actions / Docker Compose / Dockerfile show n/a because these YAML/Dockerfile formats use keyed top-level entries (services, jobs, ARG / LABEL) — those are configuration keys already captured by the Config column, not re-bindable alias declarations.
Exports

  • Lua: function foo() (top-level non-local)
  • Crystal: default-public minus private / protected modifier
  • Nim: trailing * marker
  • Cairo / Zig / Move: pub / public / entry keyword
  • HCL: output block
  • Vyper: @external / @view / @payable decorators
  • Verilog: SystemVerilog class_property minus local / protected qualifier
  • GitHub Actions: jobs.*.outputs + on.workflow_call.outputs
Heritage

  • Lua: setmetatable(..., {__index=Parent}) heuristic
  • Solidity: is X, Y, Z
  • SQL: FK REFERENCES clauses — inline column-level, table-level, and named-constraint forms
Ctor — on Go and Rust

Neither language has a language-level constructor. Go uses factory functions (NewFoo()) and Rust uses associated functions (Foo::new()) as idiomatic substitutes, but the cross-language Ctor extractor only emits NodeKind::Constructor for languages with a reserved ctor name (__init__, initialize, __construct, constructor, Class::Class).

Entry — on JavaScript and Ruby

Absence of a language-level main convention (per entry_points.rs coverage table). Entry points still surface for these languages via route handlers and framework decorators — just not via a main() symbol.

Rename n/a on markup/config rows

Markdown, GitHub Actions, Docker Compose, Dockerfile, and YAML carry keys / literal strings, not re-bindable code identifiers — ecp rename would have nothing to rewrite.

开发问答

在 agent 沟通的过程中，LLM 很容易呈现闭世界假设。对 LLM 来说，任何未知都可能被当成不存在，所以让 LLM 认知到「不知道」非常重要，这能避免 LLM 产生幻觉。

在知道「不知道」的情况下，LLM 才能深挖更深层的问题，找到实际答案，而不是因为工具掩盖了未知，让 LLM 以为不知道的事情不存在。

所以 BlindSpot 的价值不是补完整个图谱，而是诚实揭露图谱的边界。没有标出 BlindSpot 时，人类工程师可能还会怀疑这里有暗坑；但 Agent 可能会直接把「没有边」理解成「没有依赖」。这对大型系统非常危险。

实际上所有先进的 Agentic Developer 或团队都已经开始逐步采用这个机制，但更多是在工作流上实现。工作流的建立往往复杂且庞大，但通过简单的 peer 设计，就能让 code agent 在开发中彼此实时互通当前的开发信息，避免重复劳动或引入双方改动之间的冲突。

如今我们有 sub-agent 的开发模式，但这种机制只是对单一 session 的扩展。Sub-agent 只是完成 main agent 交付的任务。

通过 ecp peers，我希望达成的是一群庞大的 main agent 在互通信息的情况下完成更庞大的计划，而不只是通过文档记录来沟通。这样的设计更能实时推进彼此的进度，也能完成更大规模的设计规划。

mmap 与 rkyv 的无状态思路，取决于性能和稳定性。

启动 server 之后，server 可以拥有状态，但为了维护状态，我们需要更多复杂流程与代码去确保所有状态的一致性。每一次与 server 的交互都是成本；必要的缓存也是内存成本。诸多限制会造成性能低下。

通过 mmap，所有 agent 共享底层的公共资源，彼此不需要拥有状态，而是在近乎即时查询的静态数据上工作。实测来看，1.6 万文件、30 万级节点的 graph 构建只需要 2 到 3 秒，产生的 graph.bin 实际不到 70 MB。因为是共享的 mmap 设计，各项 CLI 查询基本落在 100 ms 以内。

这个模型对 Agent 很重要，因为 Agent 系统本来就高并发、生命周期短、容易重启、容易跨 session。无状态不只是为了快，而是为了让失败模式变少。

是。AI Agent 在软件开发里更大的挑战，正在从「能不能写对一个函数」转向「能不能在大型系统里不破坏既有的架构约束」。

单个函数的正确性可以靠类型、测试、lint、局部上下文解决；但真实系统的风险常常藏在跨文件、跨服务、跨语言、跨时间的约束里。

LLM 可以通过基础的图谱查询自己推导，但那不是稳定方案。问题不在于 LLM 不会推理，而是每次都让它从低阶节点和边重新发现架构模式，成本高、结果不一致，也容易漏掉「负空间」。所以 ECP 内置 Saga、EventTopic 这类模式检测，是把高风险、常见、可结构化的架构知识提前升级成一等信号。更准确地说，它应该是 Agent 的架构雷达：在动手改代码前，把高置信度的约束、可能的隐性耦合、需要人工验证的启发式规则明确摊开。

GitNexus 不是我的项目，而是我这个项目的起源。我在使用 GitNexus 的过程中遇到一些问题：性能、多个 daemon server，以及多个架构瓶颈，于是自主开发了 Rust 架构。

第一个临界点是常驻状态开始反过来限制 Agent 的工作流。多个 Agent、不同 worktree、不同仓库、不同分支同时查询时，daemon 模型很容易变成隐性的协调问题。第二个临界点是对查询频率的设想变了。我想要的是更接近 Agent 的 L1 / L2 cache：每次改文件前、重命名前、review 前、影响分析前，都可以毫秒级查一次。到了这个频率，Node.js daemon 的成本都会变得刺眼。

所以 Rust 无状态架构的核心判断是：把 graph 做成固定格式的 graph.bin，让每次 CLI / MCP 查询都直接 mmap，不用预热、不依赖 daemon 状态、不需要相信某个长生命周期的进程。

最早我没有想重造 merge queue。我只是想把 ecp impact 的信号喂给现有队列，所以做了 ecp dev pr-analyze，让 workflow 自动打上 area、risk、cross-pr-conflict。

但 dogfooding 之后发现，真正有价值的不是队列本身，而是「用 graph 判断 PR 是否能安全并行」。如果两个 PR 即使改的是不同文件，只要一个动到了另一个影响范围内的 symbol，就会被视为语义冲突。反过来，如果两个 PR 位于不相关的区域，且影响集合没有交集，就可以被标成低风险、无 cross-PR conflict，交给 workflow 做更积极的合并。

这项功能真正节省的不是单次 CI 时间，而是减少 PR 相互 drift 导致不断 rebase 与重跑 CI 的循环。ECP 在这里的愿景是：把 merge queue 从「按时间排队」提升成「按结构风险调度」。

传统人类团队用来管理变更的节奏并不能说是错的，而是整个流程制度上应该更自动化，以免阻碍开发。

现在 Agent coding 的速度非常快，但阻碍的反倒是人的担心和害怕。担心代码相互冲突、担心 LLM 改 A 坏 B、担心各种代码出错，这些恐惧反倒成为阻碍开发的最大问题。

随着未来每个人、每个团队、每家公司开发的项目都指数级增长，类似的工具会更重要，而性能会成为致命的关键。如何让 LLM 更快理解当前架构，而不是靠长期记忆的 context 处理，变得相对重要。我们更应该通过源代码让 LLM 了解架构，而不是通过文字记录来描述当前的代码架构，因为只有源代码才是唯一的事实。

AI Agent 时代的文档反倒会变成「流程图」最重要，因为人需要管理的是流程与架构设计。通过图表，我们能快速看到每个设计，但代码如何生成、工具如何验证、Agent 如何消费，将会逐渐变得不那么重要。

但底层的核心设计仍然应该记录，例如如何利用缓存、是否该有预热、client 超时该设多少等等。这些设计文档仍然重要，只是会抽象到更大的范围。准确地说，所有文档都会再往更高维度的设计移动。

就像我们现在写程序不会再去深究机器码如何编译、如何运行。包括目前所设计的 Egent Code Plexus，也只是当前时代下顺应趋势的过渡产物。

ECP 应该专注于成为一个极快、可信、以源代码为依据的结构感知层。

这个项目不会、也不需要成为另一个 Codex、Claude Code 或 OpenClaw，而是让这些需要执行 code agent workflow 的框架，在需要了解代码时可以选用的工具。它就是一个 LLM 专用的 grep / read 工具。

传统工具回答「这个字符串在哪里？」「这个文件的内容是什么？」，而 ECP 要回答的是：「这个 symbol 是谁？」「它被谁调用？」「它会影响哪些上游 / 下游？」「这次 diff 的结构风险是什么？」。ECP 的核心不是替 Agent 做决策，而是提供 Agent 做决策前必须知道的结构事实。

最重要的产品接口是 CLI。

MCP 在维护上比较麻烦，但因为不是每个 code agent 框架都能原生调用 CLI，所以采用了双重架构，同时用 MCP 去引导使用 CLI 调用。但更好的方式应该是让工具能直接内嵌为 CLI 工具，就像 read 那样。这对提高性能与减少 token 都是很大的帮助。

CLI 的优势是简单、维护成本低、容易测试、容易放进 CI，也没有 server 生命周期、工具注册、schema 兼容与 session 状态的问题。MCP 的价值是兼容层，而不是核心抽象。

这些设计在被 LLM 学会之前，都需要 skill 去规范与引导。就像人类还没学会用火之前，并不知道火的用途。但随着这些知识被广泛运用，大多数人应该没有上过如何用火的课程与指导。

目前仍然需要通过 skill 去规范与引导，除非哪天 LLM 内置了这类知识。但我希望 skill 不是用来约束 LLM 该如何使用工具，而是一种引导。工具应该描述它的功能，而如何使用则通过 skill 做基本引导，也能按照个人需求调整。当然更希望的是 LLM 自主理解，从而做到更广泛的运用。

「所有行动都应该从可验证的结构事实出发，而不是从上下文幻觉出发。」

任何前文都可能成为幻觉，只有即时确认的情况才可验证。这也就是为什么会想设计出 peer 功能：通过 hook / peer 达到半实时的互动，以避免开发冲突的产生。

未来愿景

“所有行动都应该从可验证的结构事实出发，而不是从上下文幻觉出发。”

在 AI Agent 时代，开发速度不再是唯一瓶颈；真正的瓶颈是信任。人类害怕 Agent 改坏系统，Agent 也容易被自己的上下文误导。Egent Code Plexus 试图把信任建立在可验证的结构事实上，让 Agent 在每一次行动前，都能快速回到唯一真相：Source Code。


如果未来每个人、每个团队、每间公司都会同时驱动更多 Agent、更多 Repo、更多变更，那真正重要的不是把更多内容塞进 context，而是拥有一个极快、可信、以结构感知为基础的底层工具。
