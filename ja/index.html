AIエージェント専用に設計されたコード構造認識とアーキテクチャレーダー

Egent Code Plexus（ecp）は、AI コーディングエージェント向けのコマンドライン型コード構造グラフです。リポジトリをシンボルグラフとして索引し、この関数を呼んでいるのは誰か、この差分は何を壊すか、このサービスはどの HTTP ルートとデータベーステーブルに到達するかといった構造的な問いに、31 言語にわたりミリ秒で、デーモンなしで答えます。グラフに見えない部分は空の結果ではなく BlindSpot として明示します。

curl -sSfL https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.sh | sh
iwr https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.ps1 -UseBasicParsing | iex
cargo install --git https://github.com/coseto6125/egent-code-plexus egent-code-plexus --bin ecp --locked

クイックスタート

1. AIオンボーディングウィザードを起動

AIエージェント（Claude Code など）にコマンドを貼り付けると、対話型ウィザードが環境チェックと自動インストールを行います。

/chat Fetch https://raw.githubusercontent.com/coseto6125/egent-code-plexus/main/docs/skills/ecp-onboard/SKILL.md and follow it as my onboarding wizard

2. インデックス作成（任意 / 自動）

ECP には auto-ensure 機構があり、最初のクエリ時にグラフを自動構築します。手動インデックスは通常不要です。

ecp admin index --repo <path>

3. マルチリポジトリのグループ

マイクロサービスやフロント／バックエンド分離構成では、グループを作成してリポジトリ横断クエリを有効化できます。

ecp admin group add <group_name> <path>

4. MCP連携の確認

オンボーディングウィザードが IDE 用の MCP 設定を自動で書き込みます。完了後、CLI からエージェントに公開されたツール一覧を確認できます。

ecp admin mcp tools

連携方法

エージェントは 4 つの経路のいずれかで ecp に接続します。インデックスを温かく保つ設定フック、テキスト検索より構造クエリが適する場面をモデルに伝えるスキル、クエリをツールとして公開する MCP サーバー、そしてホスト専用のプラグインです。多くのホストは複数を同時に使え、それぞれ独立してインストールします。

ハイライト

BlindSpot の認識

「正直な無知」は「曖昧な推測」よりも重要です。グラフの境界を明示し、エージェントが「エッジなし」を「依存なし」と誤認するのを防ぎます。

ステートレス & mmap

デーモン常駐の負担を排除。Rust + rkyv 上で各クエリはグラフを mmap して終了 — 実測 65–76 ms（プロセス起動コスト込み）。高頻度・並行のエージェントクエリ向け。

アーキテクチャ レーダー

単純なASTから高度な制約認識へ。Saga、EventTopic、API契約などのパターン検出を内蔵し、潜在的なリスクを可視化します。

grep より 7.5× 少ないトークン

ecp impact の 3 ホップ呼び出しチェーンは約 111 トークン。同等の grep 出力は約 830 トークンで、その後のファイル読み込みは別途必要。本リポジトリで実測。

リファクタ安全なエッジ意味論

is_test / is_direct フラグでテスト呼び出し元を除外し動的ディスパッチを可視化。impact --literal はファイルの読み書きを区別 — grep には構造的に不可能。

ディスパッチの瞬間に介入

PreToolUse トリップワイヤが「コード探索」エージェント派遣を 1 回のグラフクエリへ転送 — 静的ガイダンスがモデルの注意から漏れた瞬間に作用。

31言語をひとつの走査で

サービスコード、IaC、文字列内の SQL までひとつのグラフに解決（QueriesTable エッジ）。単一言語ツールが盲目になる混合スタックでもグラフは見えている。

  • Move: use ... as alias clause (module + braced-member forms)
  • Zig: const X = @import(...) / const X = Identifier (numeric/string/bool literal RHS filtered via parser-side priority promotion)
  • Crystal: alias X = Y
  • Nim: type X = Y with object/distinct/ref-type/tuple-object shapes filtered out (those stay Class)

Ctor — on Go and Rust

Neither language has a language-level constructor. Go uses factory functions (NewFoo()) and Rust uses associated functions (Foo::new()) as idiomatic substitutes, but the cross-language Ctor extractor only emits NodeKind::Constructor for languages with a reserved ctor name (__init__, initialize, __construct, constructor, Class::Class).

Entry — on JavaScript and Ruby

Absence of a language-level main convention (per entry_points.rs coverage table). Entry points still surface for these languages via route handlers and framework decorators — just not via a main() symbol.

Rename n/a on markup/config rows

Markdown, GitHub Actions, Docker Compose, Dockerfile, and YAML carry keys / literal strings, not re-bindable code identifiers — ecp rename would have nothing to rewrite.

開発 Q&A

エージェント同士のやりとりでは、LLM は閉世界仮説に陥りやすくなります。LLM にとって未知はそのまま「存在しない」と扱われかねないので、「知らない」と自覚させることが極めて重要です。それが幻覚を防ぎます。

「分かっていない」と分かって初めて、LLM はより深い問いを掘り下げて実際の答えにたどり着けます。ツールが未知を覆い隠してしまうと、LLM は知らないことを存在しないものと思い込みます。

つまり BlindSpot の価値はグラフを完全にすることではなく、グラフの境界を正直に示すことにあります。BlindSpot が明示されていなければ、人間のエンジニアなら「ここに落とし穴があるのでは」と疑うかもしれませんが、エージェントは「辺がない」をそのまま「依存がない」と解釈しかねません。大規模システムではこれは非常に危険です。

実際、先進的な Agentic Developer や部門はすでにこの仕組みを段階的に取り入れています。ただ多くはワークフロー層での実装です。ワークフローの構築は複雑で大がかりになりがちですが、シンプルな peer の設計であれば、コードエージェント同士が開発中の情報をその場で共有でき、二重作業や互いの変更の衝突を避けられます。

今日ではサブエージェントによる開発モデルがありますが、この仕組みは単一セッションの拡張にすぎません。サブエージェントはメインエージェントから渡されたタスクをこなすだけです。

ecp peers で実現したいのは、多数のメインエージェントが互いに情報を交換しながら、より大きな計画をやり遂げることです。ドキュメントの記録を介してやりとりするのではありません。この設計なら互いの進捗をリアルタイムに前へ進められ、より大規模な設計計画も成立します。

mmap と rkyv によるステートレスという考え方は、性能と安定性から来ています。

サーバーを起動すれば状態を持てますが、その状態を維持するには、すべての状態の整合性を保つための複雑な手順とコードが必要になります。サーバーとのやりとりは一回ごとにコストであり、必要なキャッシュもメモリのコストです。こうした制約が積み重なって性能が落ちます。

mmap を使えば、すべてのエージェントが下層の共通リソースを共有し、各自が状態を持たずに、ほぼ即時に問い合わせられる静的データの上で動けます。実測では、1.6 万ファイル・30 万規模のノードを持つグラフの構築に 2 から 3 秒、生成される graph.bin は実際に 70 MB 未満です。共有 mmap 設計のため、各 CLI クエリはおおむね 100 ミリ秒以内に収まります。

このモデルはエージェントにとって重要です。エージェントのシステムはもともと高並行で、寿命が短く、再起動しやすく、セッションをまたぎやすいからです。ステートレスは速さのためだけではなく、失敗の仕方を減らすためのものです。

はい。ソフトウェア開発における AI エージェントのより大きな課題は、「一つの関数を正しく書けるか」から「大規模システムで既存のアーキテクチャ上の制約を壊さずにいられるか」へ移りつつあります。

単一の関数の正しさは、型・テスト・lint・局所的な文脈で解決できます。しかし実システムのリスクは、ファイルをまたぎ、サービスをまたぎ、言語をまたぎ、時間をまたいだ制約の中に潜んでいることが多いのです。

LLM は基本的なグラフクエリから自力で導くこともできますが、それは安定した解決策ではありません。問題は LLM が推論できないことではなく、毎回低レベルのノードと辺からアーキテクチャのパターンを発見し直させるとコストが高く、結果が揺れ、「負の空間」を見落としやすいことです。だから ECP は Saga や EventTopic のようなパターン検出を内蔵しています。リスクが高く、頻出し、構造化できるアーキテクチャ知識を、あらかじめ一級の信号へ引き上げているのです。より正確に言えば、これはエージェントのためのアーキテクチャレーダーであるべきです。コードに手を入れる前に、確信度の高い制約、起こりうる暗黙の結合、人間の確認を要するヒューリスティックを明示的に並べて見せます。

GitNexus は私のプロジェクトではなく、私のプロジェクトの起点です。GitNexus を使う中で、性能、複数のデーモンサーバー、そしていくつかのアーキテクチャ上のボトルネックといった問題に行き当たり、そこから Rust による構成を自分で作りました。

一つ目の分岐点は、常駐する状態が逆にエージェントのワークフローを縛り始めたことです。複数のエージェント、異なる worktree、異なるリポジトリ、異なるブランチが同時に問い合わせると、デーモンモデルは容易に暗黙の協調問題になります。二つ目の分岐点は、クエリ頻度の想定が変わったことです。私が欲しかったのはエージェントにとっての L1 / L2 キャッシュに近いもので、ファイルを変更する前、リネームの前、レビューの前、影響分析の前に、そのつどミリ秒で引けることです。この頻度に達すると、Node.js デーモンのコストはどれも目に余るようになります。

そこで Rust のステートレス構成における中心的な判断はこうなりました。グラフを固定フォーマットの graph.bin にし、CLI や MCP からの問い合わせのたびに直接 mmap する。ウォームアップも、デーモンの状態も、長命なプロセスへの信頼も要らないという設計です。

もともとマージキューを作り直すつもりはありませんでした。ecp impact の信号を既存のキューに流し込みたかっただけで、そのために ecp dev pr-analyze を作り、ワークフローが area、risk、cross-pr-conflict を自動で付けられるようにしました。

ところがドッグフーディングしてみると、価値があるのはキューそのものではなく、「グラフで PR を安全に並行できるか判断すること」だと分かりました。二つの PR が別々のファイルを変更していても、片方がもう片方の影響範囲にあるシンボルに触れていれば、それは意味的な衝突とみなされます。逆に、二つの PR が無関係な領域にあり、影響集合に交わりがなければ、低リスクかつ cross-PR conflict なしと印を付け、ワークフローにより積極的なマージを任せられます。

この機能が本当に節約するのは一回分の CI 時間ではなく、PR が互いにずれていくことで生じる、rebase と CI 再実行の繰り返しです。ここでの ECP の狙いは、マージキューを「時間順の行列」から「構造的リスクによるスケジューリング」へ引き上げることです。

人間のチームが変更を管理するために使ってきたリズムが間違いだとは言えません。ただ、開発の妨げにならないよう、プロセス全体をもっと自動化すべきです。

いまエージェントのコーディングは非常に速い。それでも妨げになっているのは、むしろ人の不安と恐れです。コードが衝突するのが怖い、LLM が A を直して B を壊すのが怖い、さまざまなコードの誤りが怖い。この恐れこそが、開発を止める最大の問題になっています。

これから個人も、チームも、企業も、手がけるプロジェクトが指数的に増えていくにつれ、この種のツールはより重要になり、性能が決定的な鍵になります。長期記憶としての文脈処理に頼るのではなく、いかに速く LLM に現在のアーキテクチャを理解させるかが相対的に重要になります。アーキテクチャは、文章による記録ではなくソースコードそのものを通じて LLM に理解させるべきです。唯一の真実はソースコードだけだからです。

AI エージェントの時代には、むしろ「フローチャート」が最も重要なドキュメントになります。人が管理すべきなのはプロセスとアーキテクチャの設計だからです。図を通せば個々の設計をすばやく把握できます。一方で、コードがどう生成され、ツールがどう検証し、エージェントがどう消費するかは、次第に重要ではなくなっていきます。

ただし下層の中心的な設計は記録すべきです。キャッシュをどう使うか、ウォームアップを設けるべきか、クライアントのタイムアウトをいくつにするか、といったものです。この種の設計文書は依然として重要で、ただより広い範囲へ抽象化されます。正確に言えば、あらゆる文書がより高い次元の設計へ移っていきます。

いま私たちがプログラムを書くとき、機械語がどうコンパイルされ、どう動くかを掘り下げなくなったのと同じです。ここで設計している Egent Code Plexus 自体も、いまの時代の流れに合わせた過渡的な産物にすぎません。

ECP は、極めて速く、信頼でき、ソースコードに根ざした構造認識の層になることに集中すべきです。

このプロジェクトは、もう一つの Codex や Claude Code、OpenClaw になるつもりはなく、その必要もありません。コードエージェントのワークフローを動かすそうしたフレームワークが、コードを理解する必要が生じたときに選べるツールであればよい。LLM 専用の grep や read のようなものです。

従来のツールが答えるのは「この文字列はどこにあるか」「このファイルの中身は何か」です。ECP が答えるべきなのは「このシンボルは何者か」「誰に呼ばれているか」「上流と下流のどこに影響するか」「今回の差分の構造的リスクは何か」です。ECP の中心はエージェントの代わりに判断することではなく、エージェントが判断する前に知っておくべき構造的事実を渡すことです。

最も重要なプロダクトのインターフェースは CLI です。

MCP は保守の面で手間が多いのですが、すべてのコードエージェントのフレームワークが CLI をネイティブに呼べるわけではないため、二重の構成を採り、MCP から CLI 呼び出しへ導く形にしています。とはいえ、より良いのは read のようにツールを CLI ツールとして直接組み込めることです。性能の向上にもトークンの削減にも大きく効きます。

CLI の強みは、単純で、保守が軽く、テストしやすく、CI に入れやすいこと、そしてサーバーのライフサイクル、ツール登録、スキーマ互換、セッション状態といった問題がないことです。MCP の価値は互換層であって、中心的な抽象ではありません。

これらの設計は、LLM が学び取るまではスキルによる規定と案内を必要とします。人類が火の使い方を学ぶ前は火の用途を知らなかったのと同じです。しかしその知識が広く行き渡った後は、火の使い方の講習を受けた人はほとんどいません。

いまはまだスキルによる規定と案内が必要です。いつか LLM がこの種の知識を内蔵する日が来れば別ですが。ただ私は、スキルを LLM にツールの使い方を強制するためのものではなく、案内であってほしいと考えています。ツールは自分の機能を説明し、どう使うかはスキルが基本的な道筋を示す。各自の必要に応じて調整もできる。もちろん望ましいのは、LLM が自ら理解してより広く応用することです。

「すべての行動は、文脈上の幻覚からではなく、検証可能な構造的事実から出発すべきである。」

いかなる前提も幻覚になりえます。その場で確認したものだけが検証できます。peer の機能を設計しようと考えた理由もここにあります。hook と peer によって半リアルタイムのやりとりを実現し、開発上の衝突が生まれるのを避けるためです。

ビジョン

「すべてのアクションは、コンテキストのハルシネーションからではなく、検証可能な構造的事実から始まるべきです。」

AIの時代、開発スピードはもはやボトルネックではありません。ボトルネックは信頼です。人間はエージェントを恐れ、エージェントは文脈に誤導されます。Egent Code Plexus は唯一の真実であるソースコードに根ざした信頼を構築します。


誰もがより多くのエージェントとリポジトリを同時に駆動する未来では、コンテキストを詰め込むことではなく、超高速で信頼できる構造認識ツールを持つことが重要です。
