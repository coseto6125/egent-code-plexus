ecp vs codegraph vs GitNexus

Trois outils de graphe de code, mêmes checkouts, même machine.

Tous trois construisent un graphe du dépôt et répondent à des questions structurelles. Ils diffèrent par ce qu'ils optimisent : codegraph et GitNexus sont des services Node qui gardent le graphe en mémoire ou dans SQLite, tandis qu'ecp est un binaire Rust sans état qui charge un graphe préconstruit via mmap : une requête coûte un démarrage de processus, pas un temps de chauffe. Les chiffres ci-dessous sont les mesures du projet lui-même, publiées avec les conditions qui les ont produites.

Comment ces chiffres ont été mesurés

  • Versions — ecp 0.16.2 · codegraph 1.6.2 · gitnexus 1.6.12 (2026-10-22)
  • Matériel — AMD Ryzen 9 9950X, Linux (WSL2), épinglé sur 8 cœurs logiques
  • Mêmes checkouts, même machine, un outil à la fois. Les trois plafonnés à 1 MiB par fichier. Médianes sur 3 à 5 exécutions pour l'indexation et sur 7 pour les requêtes ; les rapports d'indexation à froid viennent d'exécutions entrelacées. ecp est une CLI sans état à usage unique : chaque latence inclut le démarrage complet du processus, sans démon ni préchauffage.

Ce que ces chiffres ne disent pas

C'est une machine, un jeu de versions, deux corpus. Ces chiffres ne disent rien de l'API qu'il vous faut, de la couverture de langages face à votre stack, ni du comportement sur un dépôt qui ne ressemble pas à ces deux-là. Un outil qui perd sur l'indexation à froid peut rester le bon choix s'il répond à une question que les autres ne savent pas traiter. Rejouez les mesures sur votre propre dépôt avant de trancher : les commandes sont dans le README de chaque projet.
