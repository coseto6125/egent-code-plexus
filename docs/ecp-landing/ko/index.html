Egent Code Plexus v0.12.1

Built for agents, not IDEs.

AI 에이전트를 위해 특별히 설계된 코드 구조 인식 및 아키텍처 레이더

Egent Code Plexus(ecp)는 AI 코딩 에이전트를 위한 명령줄 코드 구조 그래프입니다. 저장소를 심볼 그래프로 색인하고 이 함수를 호출하는 것은 무엇인지, 이 변경이 무엇을 깨뜨리는지, 이 서비스가 어떤 HTTP 라우트와 데이터베이스 테이블에 닿는지를 31개 언어에 걸쳐 밀리초 단위로, 데몬 없이 답합니다. 그래프가 보지 못하는 부분은 빈 결과 대신 BlindSpot으로 명시합니다.

curl -sSfL https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.sh | sh
iwr https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.ps1 -UseBasicParsing | iex
cargo install --git https://github.com/coseto6125/egent-code-plexus egent-code-plexus --bin ecp --locked

빠른 시작

1. AI 온보딩 마법사 실행

AI 에이전트(예: Claude Code)에 명령을 붙여넣으면 대화형 마법사가 환경 점검과 자동 설치를 수행합니다.

/chat Fetch https://raw.githubusercontent.com/coseto6125/egent-code-plexus/main/docs/skills/ecp-onboard/SKILL.md and follow it as my onboarding wizard

2. 인덱스 생성(선택 / 자동)

ECP는 auto-ensure 메커니즘을 내장해 첫 쿼리 시 그래프를 자동 생성하므로 수동 인덱싱은 대개 불필요합니다.

ecp admin index --repo <path>

3. 멀티 레포 그룹

마이크로서비스나 프런트/백엔드 분리 구조라면 그룹을 만들어 레포 간 쿼리를 활성화하세요.

ecp admin group add <group_name> <path>

4. MCP 통합 확인

온보딩 마법사가 IDE의 MCP 설정을 자동으로 작성합니다. 완료 후 CLI에서 에이전트에 노출된 도구 목록을 확인하세요.

ecp admin mcp tools

하이라이트

BlindSpot 인식

"솔직한 모름"이 "모호한 추측"보다 중요합니다. 그래프 경계를 명시하여 에이전트가 의존성이 없다고 착각하는 것을 방지합니다.

상태 비저장 & mmap

상주 데몬의 부담 제거. Rust + rkyv 기반으로 각 쿼리는 그래프를 mmap 후 종료 — 실측 65–76 ms(프로세스 기동 비용 포함). 고빈도 병렬 에이전트 쿼리를 위한 설계.

아키텍처 레이더

단순한 AST를 넘어 고급 아키텍처 제약 조건 인식. Saga, EventTopic, API 계약 패턴을 감지하여 위험을 조기에 드러냅니다.

grep보다 7.5× 적은 토큰

ecp impact의 3홉 호출 체인은 약 111 토큰. 동등한 grep 출력은 약 830 토큰이며 이후 파일 읽기는 별도입니다. 본 저장소에서 실측.

리팩터링 안전한 엣지 시맨틱

is_test / is_direct 플래그로 테스트 호출자를 제외하고 동적 디스패치를 드러냅니다. impact --literal은 파일 읽기와 쓰기를 구분 — grep은 구조적으로 불가능.

디스패치 순간에 개입

PreToolUse 트립와이어가 '코드 탐색' 에이전트 디스패치를 그래프 쿼리 한 번으로 전환 — 정적 가이드가 모델의 주의에서 사라진 바로 그 순간에 작동.

31개 언어, 단일 순회

서비스 코드, IaC, 문자열 안의 SQL까지 하나의 그래프로 해석(QueriesTable 엣지). 단일 언어 도구가 어두워지는 혼합 스택에서도 그래프는 밝게 유지됩니다.

Named

  • Lua: local M = require(...) and dotted-path bindings (plain literal RHS filtered)
  • Cairo: use X as Y + type X = Y
  • Move: use ... as alias clause (module + braced-member forms)
  • Zig: const X = @import(...) / const X = Identifier (numeric/string/bool literal RHS filtered via parser-side priority promotion)
  • Crystal: alias X = Y
  • Nim: type X = Y with object/distinct/ref-type/tuple-object shapes filtered out (those stay Class)
  • Vyper: from X import Y as Z / import X as Y (source-line scan — grammar can't AST-parse the as clause)
  • Solidity: using L for T directives + type C is uint256 user-defined value types
  • HCL: locals { } block attributes (output blocks remain Const)
  • SQL: top-level CREATE VIEW v AS … (column aliases SELECT x AS y not captured)
  • Verilog: SystemVerilog typedef declarations

Ctor — on Go and Rust

Neither language has a language-level constructor. Go uses factory functions (NewFoo()) and Rust uses associated functions (Foo::new()) as idiomatic substitutes, but the cross-language Ctor extractor only emits NodeKind::Constructor for languages with a reserved ctor name (__init__, initialize, __construct, constructor, Class::Class).

Entry — on JavaScript and Ruby

Absence of a language-level main convention (per entry_points.rs coverage table). Entry points still surface for these languages via route handlers and framework decorators — just not via a main() symbol.

Rename n/a on markup/config rows

Markdown, GitHub Actions, Docker Compose, Dockerfile, and YAML carry keys / literal strings, not re-bindable code identifiers — ecp rename would have nothing to rewrite.

개발 Q&A

에이전트끼리 주고받는 과정에서 LLM은 닫힌 세계 가정에 빠지기 쉽습니다. LLM에게 모르는 것은 곧 존재하지 않는 것으로 취급되기 쉬우므로, '모른다'는 사실을 인지시키는 일이 매우 중요합니다. 그것이 환각을 막습니다.

'모른다'는 것을 알아야 LLM이 더 깊은 문제까지 파고들어 실제 답에 닿을 수 있습니다. 도구가 모름을 덮어버리면 LLM은 모르는 것이 아예 존재하지 않는다고 믿게 됩니다.

그래서 BlindSpot의 가치는 그래프를 완성하는 데 있지 않고 그래프의 경계를 정직하게 드러내는 데 있습니다. BlindSpot이 표시되지 않으면 사람 엔지니어는 함정이 있는지 의심이라도 하지만, 에이전트는 '간선이 없음'을 그대로 '의존이 없음'으로 해석할 수 있습니다. 대형 시스템에서 이는 매우 위험합니다.

사실 앞서가는 Agentic Developer나 조직은 이미 이 방식을 단계적으로 도입하고 있습니다. 다만 대부분 워크플로 계층에서 구현합니다. 워크플로를 만드는 일은 복잡하고 규모가 커지기 쉽지만, 단순한 peer 설계만으로도 코드 에이전트들이 개발 중인 정보를 서로 즉시 공유하여 중복 작업이나 서로의 변경이 충돌하는 문제를 피할 수 있습니다.

오늘날 서브 에이전트 개발 모델이 있지만, 이 구조는 단일 세션의 확장에 지나지 않습니다. 서브 에이전트는 메인 에이전트가 넘긴 작업을 수행할 뿐입니다.

ecp peers로 이루고 싶은 것은, 다수의 메인 에이전트가 서로 정보를 주고받으며 더 큰 계획을 완성하는 일입니다. 문서 기록을 통해 소통하는 방식이 아닙니다. 이런 설계라야 서로의 진행을 실시간으로 밀어 올리고 더 큰 규모의 설계까지 해낼 수 있습니다.

mmap과 rkyv를 쓴 무상태라는 개념은 성능과 안정성에서 나왔습니다.

서버를 띄우면 상태를 가질 수 있지만, 그 상태를 유지하려면 모든 상태의 일관성을 보장하기 위한 복잡한 절차와 코드가 필요합니다. 서버와의 상호작용은 매번 비용이고, 필요한 캐시도 메모리 비용입니다. 이런 제약이 쌓여 성능이 떨어집니다.

mmap을 쓰면 모든 에이전트가 하부의 공통 자원을 공유하고, 각자 상태를 갖지 않은 채 사실상 즉시 조회 가능한 정적 데이터 위에서 일합니다. 실측으로 1.6만 개 파일, 30만 규모 노드의 그래프를 만드는 데 2~3초가 걸리고 생성되는 graph.bin은 실제로 70MB 미만입니다. 공유 mmap 설계이므로 각 CLI 조회는 대체로 100밀리초 안에 들어옵니다.

이 모델은 에이전트에게 중요합니다. 에이전트 시스템은 본래 동시성이 높고 수명이 짧으며 쉽게 재시작되고 세션을 자주 넘나들기 때문입니다. 무상태는 빠르기 위해서만이 아니라 실패하는 방식을 줄이기 위한 선택입니다.

그렇습니다. 소프트웨어 개발에서 AI 에이전트의 더 큰 과제는 '함수 하나를 제대로 쓸 수 있는가'에서 '대형 시스템에서 기존 아키텍처의 제약을 깨뜨리지 않을 수 있는가'로 옮겨가고 있습니다.

함수 하나의 정확성은 타입, 테스트, lint, 국소적인 문맥으로 해결됩니다. 그러나 실제 시스템의 위험은 파일과 서비스, 언어와 시간에 걸친 제약 속에 숨어 있는 경우가 많습니다.

LLM이 기본적인 그래프 조회만으로 스스로 추론할 수도 있지만 그것은 안정적인 해법이 아닙니다. 문제는 LLM이 추론하지 못한다는 것이 아니라, 매번 저수준 노드와 간선에서 아키텍처 패턴을 다시 발견하게 하면 비용이 크고 결과가 흔들리며 '음의 공간'을 놓치기 쉽다는 점입니다. 그래서 ECP는 Saga나 EventTopic 같은 패턴 탐지를 내장합니다. 위험이 크고 자주 나타나며 구조화할 수 있는 아키텍처 지식을 미리 일급 신호로 올려두는 것입니다. 더 정확히 말하면 이것은 에이전트를 위한 아키텍처 레이더여야 합니다. 코드에 손대기 전에 확신도가 높은 제약, 있을 수 있는 암묵적 결합, 사람의 확인이 필요한 휴리스틱을 명시적으로 펼쳐 보여줍니다.

GitNexus는 제 프로젝트가 아니라 제 프로젝트의 출발점입니다. GitNexus를 쓰면서 성능, 여러 개의 데몬 서버, 그리고 몇 가지 구조적 병목 같은 문제를 만났고, 거기서 Rust 기반 구조를 직접 만들게 되었습니다.

첫 번째 분기점은 상주하는 상태가 오히려 에이전트의 작업 흐름을 제약하기 시작했다는 것입니다. 여러 에이전트가 서로 다른 worktree, 다른 저장소, 다른 브랜치에서 동시에 조회하면 데몬 모델은 쉽게 암묵적인 협조 문제가 됩니다. 두 번째 분기점은 조회 빈도에 대한 상상이 달라졌다는 것입니다. 제가 원한 것은 에이전트에게 L1 / L2 캐시에 가까운 것으로, 파일을 고치기 전, 이름을 바꾸기 전, 리뷰 전, 영향 분석 전에 매번 밀리초 단위로 물어볼 수 있는 수준입니다. 이 빈도에 이르면 Node.js 데몬의 비용은 하나같이 눈에 거슬리게 됩니다.

그래서 Rust 무상태 구조의 핵심 판단은 이렇습니다. 그래프를 고정 형식의 graph.bin으로 만들고, CLI나 MCP의 조회마다 곧바로 mmap한다. 예열도, 데몬의 상태도, 오래 사는 프로세스에 대한 신뢰도 필요 없게 만드는 것입니다.

처음부터 머지 큐를 다시 만들 생각은 없었습니다. ecp impact의 신호를 기존 큐에 넣고 싶었을 뿐이고, 그래서 ecp dev pr-analyze를 만들어 워크플로가 area, risk, cross-pr-conflict를 자동으로 붙이게 했습니다.

그런데 직접 써보니 가치 있는 것은 큐 자체가 아니라 '그래프로 PR을 안전하게 병행할 수 있는지 판단하는 일'이었습니다. 두 PR이 서로 다른 파일을 고치더라도 한쪽이 다른 쪽의 영향 범위 안에 있는 심볼을 건드리면 의미적 충돌로 봅니다. 반대로 두 PR이 무관한 영역에 있고 영향 집합이 겹치지 않으면 저위험이며 cross-PR conflict 없음으로 표시해, 워크플로가 더 적극적으로 병합하도록 맡길 수 있습니다.

이 기능이 실제로 아끼는 것은 한 번의 CI 시간이 아니라, PR들이 서로 어긋나면서 반복되는 rebase와 CI 재실행의 순환입니다. 여기서 ECP의 지향은 머지 큐를 '시간 순서로 줄 세우기'에서 '구조적 위험에 따른 스케줄링'으로 끌어올리는 것입니다.

사람으로 이루어진 팀이 변경을 관리해 온 리듬이 틀렸다고 할 수는 없습니다. 다만 개발을 가로막지 않도록 전체 절차가 더 자동화되어야 합니다.

지금 에이전트의 코딩 속도는 매우 빠릅니다. 그런데 가로막는 것은 오히려 사람의 걱정과 두려움입니다. 코드가 충돌할까 봐, LLM이 A를 고치다 B를 망칠까 봐, 온갖 코드 오류가 날까 봐 하는 두려움이 개발을 막는 가장 큰 문제가 되었습니다.

앞으로 개인과 팀과 회사가 다루는 프로젝트가 기하급수적으로 늘어날수록 이런 도구는 더 중요해지고 성능이 결정적인 열쇠가 됩니다. 장기 기억으로서의 문맥 처리에 기대는 대신, 어떻게 하면 LLM이 현재 아키텍처를 더 빨리 이해하게 할지가 상대적으로 중요해집니다. 아키텍처는 글로 남긴 기록이 아니라 소스 코드 자체를 통해 LLM이 이해하게 해야 합니다. 유일한 진실은 소스 코드뿐이기 때문입니다.

AI 에이전트 시대에는 오히려 '흐름도'가 가장 중요한 문서가 됩니다. 사람이 관리해야 할 것은 프로세스와 아키텍처 설계이기 때문입니다. 도표를 통하면 각각의 설계를 빠르게 파악할 수 있습니다. 반면 코드가 어떻게 생성되고 도구가 어떻게 검증하며 에이전트가 어떻게 소비하는지는 점차 덜 중요해집니다.

다만 하부의 핵심 설계는 여전히 기록해야 합니다. 캐시를 어떻게 활용할지, 예열을 둘지, 클라이언트 타임아웃을 얼마로 할지 같은 것들입니다. 이런 설계 문서는 여전히 중요하며, 다만 더 넓은 범위로 추상화됩니다. 정확히 말하면 모든 문서가 더 높은 차원의 설계로 옮겨갑니다.

오늘날 프로그램을 쓰면서 기계어가 어떻게 컴파일되고 실행되는지 더 파고들지 않는 것과 같습니다. 지금 설계하고 있는 Egent Code Plexus 자체도 이 시대의 흐름에 맞춘 과도기적 산물일 뿐입니다.

ECP는 아주 빠르고 신뢰할 수 있으며 소스 코드에 근거한 구조 인식 계층이 되는 데 집중해야 합니다.

이 프로젝트는 또 하나의 Codex나 Claude Code, OpenClaw가 될 생각이 없고 그럴 필요도 없습니다. 코드 에이전트 워크플로를 돌리는 그런 프레임워크들이 코드를 이해해야 할 때 골라 쓸 수 있는 도구면 됩니다. LLM 전용 grep이자 read 같은 것입니다.

전통적인 도구는 '이 문자열이 어디에 있는가', '이 파일의 내용은 무엇인가'에 답합니다. ECP가 답해야 할 것은 '이 심볼은 무엇인가', '누가 호출하는가', '상류와 하류의 무엇에 영향을 주는가', '이번 diff의 구조적 위험은 무엇인가'입니다. ECP의 핵심은 에이전트를 대신해 결정하는 것이 아니라, 결정하기 전에 반드시 알아야 할 구조적 사실을 건네는 것입니다.

가장 중요한 제품 인터페이스는 CLI입니다.

MCP는 유지보수 면에서 번거로움이 많지만, 모든 코드 에이전트 프레임워크가 CLI를 네이티브로 호출할 수 있는 것은 아니어서 이중 구조를 택했고, MCP가 CLI 호출로 안내하도록 했습니다. 그래도 더 나은 방식은 read처럼 도구를 CLI 도구로 곧바로 내장할 수 있게 하는 것입니다. 성능을 높이고 토큰을 줄이는 데 크게 도움이 됩니다.

CLI의 장점은 단순하고, 유지보수가 가볍고, 테스트하기 쉽고, CI에 넣기 쉽다는 점, 그리고 서버 수명 주기나 도구 등록, 스키마 호환, 세션 상태 같은 문제가 없다는 점입니다. MCP의 가치는 호환 계층이지 핵심 추상이 아닙니다.

이런 설계들은 LLM이 익히기 전까지는 스킬로 규정하고 안내해야 합니다. 사람이 불을 다루는 법을 배우기 전에는 불의 쓰임을 몰랐던 것과 같습니다. 그러나 그 지식이 널리 쓰이게 된 뒤로는 불 사용법 강습을 들은 사람이 거의 없습니다.

지금은 여전히 스킬을 통한 규정과 안내가 필요합니다. 언젠가 LLM이 이런 지식을 내장하게 된다면 이야기가 달라지겠지요. 다만 저는 스킬이 LLM에게 도구 사용법을 강제하는 것이 아니라 안내이기를 바랍니다. 도구는 자기 기능을 설명하고, 어떻게 쓰는지는 스킬이 기본적인 길을 보여주며, 각자의 필요에 따라 조정할 수 있어야 합니다. 물론 더 바라는 것은 LLM이 스스로 이해해 더 넓게 응용하는 것입니다.

「모든 행동은 문맥의 환각이 아니라 검증 가능한 구조적 사실에서 출발해야 한다.」

앞선 어떤 문맥도 환각이 될 수 있고, 그 자리에서 확인한 것만이 검증됩니다. peer 기능을 설계하려 한 이유도 여기에 있습니다. hook과 peer로 반실시간 상호작용을 이뤄 개발 충돌이 생기는 것을 피하려는 것입니다.

비전

"모든 행동은 컨텍스트의 환각이 아닌 검증 가능한 구조적 사실에서 출발해야 합니다."

AI 에이전트 시대에 진정한 병목 현상은 신뢰입니다. 인간은 에이전트를 두려워하고 에이전트는 문맥에 현혹됩니다. Egent Code Plexus는 항상 소스 코드로 돌아가도록 신뢰를 구축합니다.


모두가 더 많은 에이전트를 동시에 구동하는 미래에는 컨텍스트를 채우는 것보다 초고속의 신뢰할 수 있는 구조 인식 도구를 갖는 것이 중요합니다.
