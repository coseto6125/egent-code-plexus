ecp vs codegraph vs GitNexus

Three code-graph tools, same checkouts, same machine.

All three build a graph of a repository and answer structural questions about it. They differ in what they are optimised for: codegraph and GitNexus are Node services that keep a graph in memory or in SQLite, while ecp is a stateless Rust binary that memory-maps a prebuilt graph, so a query costs one process start rather than a warm-up. The numbers below are the project's own measurements, published with the conditions that produced them.

How these were measured

  • Versions — ecp 0.4.2 · codegraph 0.9.4 · gitnexus 1.6.5
  • Hardware — AMD Ryzen 9 9950X (16 logical), Linux
  • Same checkouts, same machine. All tools capped at a 1 MiB max-file-size threshold where configurable (gitnexus hard-codes 512 KB). ecp medians over 5–7 runs. ecp is a stateless one-shot CLI, so every latency includes full process startup — no daemon, no warm-up.

What these numbers do not tell you

They are one machine, one set of versions, two corpora. They say nothing about which tool has the API you want, whether its language coverage matches your stack, or how it behaves on a repository shaped unlike these two. A tool that loses on cold index may still be the right choice if it answers a question the others cannot. Re-run them on your own repository before deciding — the commands are in each project's README.
