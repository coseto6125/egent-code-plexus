ecp vs codegraph vs GitNexus

Drei Code-Graph-Tools, gleiche Checkouts, gleiche Maschine.

Alle drei bauen einen Graphen über ein Repository und beantworten strukturelle Fragen dazu. Sie unterscheiden sich darin, worauf sie optimiert sind: codegraph und GitNexus sind Node-Services, die einen Graphen im Speicher oder in SQLite halten, während ecp ein zustandsloses Rust-Binary ist, das einen vorgebauten Graphen per mmap einbindet – eine Abfrage kostet also einen Prozessstart statt einer Aufwärmphase. Die Zahlen unten sind die eigenen Messungen des Projekts, veröffentlicht mit den Bedingungen, unter denen sie entstanden sind.

So wurde gemessen

  • Versionen — ecp 0.16.2 · codegraph 1.6.2 · gitnexus 1.6.12 (2026-10-22)
  • Hardware — AMD Ryzen 9 9950X, Linux (WSL2), auf 8 logische Kerne festgelegt
  • Gleiche Checkouts, gleiche Maschine, ein Werkzeug nach dem anderen. Alle drei mit 1 MiB Obergrenze pro Datei. Mediane über 3–5 Indexläufe und 7 Abfragen; die Cold-Index-Verhältnisse stammen aus verschränkten Läufen. ecp ist ein zustandsloses One-Shot-CLI, daher enthält jede Latenz den vollständigen Prozessstart – kein Daemon, kein Aufwärmen.

Was diese Zahlen nicht verraten

Sie stammen von einer Maschine, einem Versionsstand, zwei Korpora. Sie sagen nichts darüber, welches Tool die API hat, die du brauchst, ob die Sprachabdeckung zu deinem Stack passt oder wie es sich auf einem Repository verhält, das anders geschnitten ist als diese beiden. Ein Tool, das beim Cold Index verliert, kann trotzdem die richtige Wahl sein, wenn es eine Frage beantwortet, die die anderen nicht können. Miss auf deinem eigenen Repository nach, bevor du entscheidest – die Befehle stehen im README des jeweiligen Projekts.

Zahlen zuletzt aktualisiert für ecp 0.16.3. Korrekturen gern als Issues.
