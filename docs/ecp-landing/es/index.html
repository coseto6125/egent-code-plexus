Egent Code Plexus v0.13.1

Built for agents, not IDEs.

Conciencia de la estructura del código y radar de arquitectura diseñado para Agentes de IA.

Egent Code Plexus (ecp) es un grafo de inteligencia de código de línea de comandos para agentes de IA. Indexa un repositorio como grafo de símbolos y responde preguntas estructurales directamente: qué funciones llaman a esta, qué rompe este cambio, a qué rutas HTTP y tablas de base de datos llega este servicio, en 31 lenguajes, en milisegundos y sin demonio. Donde el grafo no ve algo lo dice con un registro BlindSpot en lugar de devolver un resultado vacío que parece prueba de ausencia.

curl -sSfL https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.sh | sh
iwr https://github.com/coseto6125/egent-code-plexus/releases/latest/download/install.ps1 -UseBasicParsing | iex
cargo install --git https://github.com/coseto6125/egent-code-plexus egent-code-plexus --bin ecp --locked

Inicio rápido

1. Inicia el asistente de incorporación

Pega el comando en tu agente de IA (p. ej. Claude Code) para activar un asistente interactivo que verifica el entorno e instala todo por ti.

/chat Fetch https://raw.githubusercontent.com/coseto6125/egent-code-plexus/main/docs/skills/ecp-onboard/SKILL.md and follow it as my onboarding wizard

2. Construye el índice (opcional / automático)

ECP incluye un mecanismo auto-ensure: el grafo se construye automáticamente en tu primera consulta, por lo que indexar manualmente suele ser innecesario.

ecp admin index --repo <path>

3. Grupos multi-repo

Para microservicios o arquitecturas con frontend/backend separados, crea un grupo para habilitar consultas entre repos.

ecp admin group add <group_name> <path>

4. Verifica la integración MCP

El asistente escribe la configuración MCP de tu IDE automáticamente. Después, lista las herramientas expuestas a tu agente desde la CLI.

ecp admin mcp tools

Integraciones

Un agente llega a ecp por uno de cuatro canales: hooks de configuración que mantienen el índice caliente, una skill que indica cuándo una consulta estructural gana a una búsqueda de texto, un servidor MCP que expone las consultas como herramientas, o un plugin propio del host. La mayoría de los hosts admite varios, y cada uno se instala por separado.

Destacados

Conciencia de BlindSpot

La "ignorancia honesta" es mejor que las "conjeturas vagas". Marca límites del grafo para evitar que los Agentes asuman falsas dependencias.

Sin estado & mmap

Sin demonios que cuidar. Sobre Rust + rkyv, cada consulta hace mmap del grafo y termina — 65–76 ms medidos, coste de arranque incluido. Hecho para consultas de agentes concurrentes y de alta frecuencia.

Radar de Arquitectura

Detección integrada de patrones como Saga, EventTopics y contratos de API. Elevando la conciencia a las restricciones arquitectónicas.

7,5× menos tokens que grep

Una cadena de llamadas de 3 saltos de ecp impact cuesta ~111 tokens; el volcado equivalente de grep ~830 — antes de las lecturas de archivos que grep aún necesita. Medido en vivo en este repositorio.

Semántica de aristas segura para refactors

Los flags is_test / is_direct excluyen llamadores de test y exponen el dispatch dinámico; impact --literal distingue lecturas de escrituras — algo que grep estructuralmente no puede.

Intercepta en el momento del despacho

Un tripwire PreToolUse redirige los despachos de agentes "explora el código" a una sola consulta del grafo — actuando justo cuando la guía estática ya se ha perdido de la atención del modelo.

31 lenguajes, un solo recorrido

Código de servicios, IaC y SQL dentro de literales se resuelven en un solo grafo (aristas QueriesTable) — el grafo sigue iluminado justo donde los repos políglotas dejan a oscuras a las herramientas monolenguaje.

  • Lua: require + binding alias
  • Dockerfile: FROM <base>
  • GitHub Actions: uses: directives — public tag/SHA refs, local composites, reusable workflows, cross-repo workflows
Named

  • Bash: alias command
  • Lua: local M = require(...) and dotted-path bindings (plain literal RHS filtered)
  • Cairo: use X as Y + type X = Y
  • Move: use ... as alias clause (module + braced-member forms)
  • Zig: const X = @import(...) / const X = Identifier (numeric/string/bool literal RHS filtered via parser-side priority promotion)
  • Crystal: alias X = Y
  • Nim: type X = Y with object/distinct/ref-type/tuple-object shapes filtered out (those stay Class)
  • Vyper: from X import Y as Z / import X as Y (source-line scan — grammar can't AST-parse the as clause)
  • Solidity: using L for T directives + type C is uint256 user-defined value types
  • HCL: locals { } block attributes (output blocks remain Const)
  • SQL: top-level CREATE VIEW v AS … (column aliases SELECT x AS y not captured)
  • Verilog: SystemVerilog typedef declarations
  • C: typedef + #define / preproc_function_def + extern declarations (include-guard macros filtered; classified as Alias/Constant/Macro/Flag)
  • Swift: typealias declarations + @objc(extName) rename attributes
  • Ruby: alias keyword + alias_method + constant assignment (MyConst = Other::Constant) + def_delegator / def_delegators / delegate (with Forwardable mixin detection; cross-file include Foo propagation resolved via resolver Tier 2.75 HeritageScoped)
  • GitHub Actions / Docker Compose / Dockerfile show n/a because these YAML/Dockerfile formats use keyed top-level entries (services, jobs, ARG / LABEL) — those are configuration keys already captured by the Config column, not re-bindable alias declarations.
Exports

  • Lua: function foo() (top-level non-local)
  • Crystal: default-public minus private / protected modifier
  • Nim: trailing * marker
  • Cairo / Zig / Move: pub / public / entry keyword
  • HCL: output block
  • Vyper: @external / @view / @payable decorators
  • Verilog: SystemVerilog class_property minus local / protected qualifier
  • GitHub Actions: jobs.*.outputs + on.workflow_call.outputs
Heritage

  • Lua: setmetatable(..., {__index=Parent}) heuristic
  • Solidity: is X, Y, Z
  • SQL: FK REFERENCES clauses — inline column-level, table-level, and named-constraint forms
Ctor — on Go and Rust

Neither language has a language-level constructor. Go uses factory functions (NewFoo()) and Rust uses associated functions (Foo::new()) as idiomatic substitutes, but the cross-language Ctor extractor only emits NodeKind::Constructor for languages with a reserved ctor name (__init__, initialize, __construct, constructor, Class::Class).

Entry — on JavaScript and Ruby

Absence of a language-level main convention (per entry_points.rs coverage table). Entry points still surface for these languages via route handlers and framework decorators — just not via a main() symbol.

Rename n/a on markup/config rows

Markdown, GitHub Actions, Docker Compose, Dockerfile, and YAML carry keys / literal strings, not re-bindable code identifiers — ecp rename would have nothing to rewrite.

Q&A de Desarrollo

En la comunicación entre agentes, un LLM cae con facilidad en la hipótesis de mundo cerrado: para él, lo desconocido tiende a tratarse como inexistente. Por eso es fundamental que el modelo reconozca que «no lo sabe». Eso es lo que evita las alucinaciones.

Solo sabiendo qué ignora puede el LLM profundizar hasta encontrar la respuesta real. Si la herramienta tapa ese desconocimiento, el modelo acaba creyendo que lo que no sabe sencillamente no existe.

Así, el valor de BlindSpot no está en completar el grafo, sino en mostrar con honestidad sus límites. Sin BlindSpots marcados, un ingeniero humano al menos sospecharía que hay una trampa; un agente puede interpretar directamente «no hay arista» como «no hay dependencia». En sistemas grandes eso es peligrosísimo.

De hecho, los Agentic Developers y los equipos más avanzados ya están adoptando este mecanismo poco a poco, aunque casi siempre implementado en la capa de flujo de trabajo. Construir flujos de trabajo suele ser complejo y voluminoso, pero con un diseño de peers sencillo los agentes de código pueden compartir al instante en qué están trabajando, y así evitar trabajo duplicado o conflictos entre sus cambios.

Hoy tenemos el modelo de subagentes, pero ese mecanismo es apenas una extensión de una sola sesión: el subagente se limita a completar la tarea que le pasa el agente principal.

Con ecp peers lo que busco es que un conjunto amplio de agentes principales, intercambiando información entre sí, complete planes mucho mayores, en lugar de comunicarse a través de documentos. Un diseño así permite que cada uno haga avanzar al otro en tiempo real y que se sostenga una planificación de mayor escala.

La idea de no tener estado, con mmap y rkyv, viene del rendimiento y de la estabilidad.

Un servidor en marcha puede tener estado, pero mantenerlo exige procesos y código complejos para garantizar la consistencia de todo ese estado. Cada interacción con el servidor es un coste, y las cachés necesarias son coste de memoria. Esas restricciones acumuladas degradan el rendimiento.

Con mmap, todos los agentes comparten el mismo recurso de base: ninguno necesita estado propio y todos trabajan sobre datos estáticos consultables de forma casi inmediata. En mediciones reales, construir el grafo de 16.000 archivos y del orden de 300.000 nodos lleva de 2 a 3 segundos, y el graph.bin resultante ocupa menos de 70 MB. Al ser un mmap compartido, las consultas del CLI se quedan en general por debajo de 100 ms.

Este modelo importa para los agentes porque sus sistemas son de por sí muy concurrentes, de vida corta, propensos a reiniciarse y a cruzar sesiones. Prescindir del estado no busca solo velocidad: busca reducir las formas en que algo puede fallar.

Sí. En el desarrollo de software, el reto mayor de los agentes de IA se está desplazando de «¿sabe escribir bien una función?» a «¿es capaz de no romper las restricciones arquitectónicas ya existentes en un sistema grande?».

La corrección de una función suelta se resuelve con tipos, pruebas, lint y contexto local. Pero el riesgo de un sistema real suele esconderse en restricciones que cruzan archivos, servicios, lenguajes y tiempo.

Un LLM puede deducirlo por su cuenta a partir de consultas básicas al grafo, pero esa no es una solución estable. El problema no es que el LLM no razone, sino que hacerle redescubrir cada vez los patrones arquitectónicos desde nodos y aristas de bajo nivel sale caro, da resultados inconsistentes y deja escapar el «espacio negativo». Por eso ECP incorpora detección de patrones como Saga o EventTopic: eleva de antemano a señal de primera clase el conocimiento arquitectónico que es arriesgado, frecuente y estructurable. Dicho con más precisión, debería ser el radar de arquitectura del agente: antes de tocar el código, deja a la vista las restricciones de alta confianza, los acoplamientos implícitos posibles y las heurísticas que requieren verificación humana.

GitNexus no es mi proyecto: es el origen de mi proyecto. Usándolo me encontré con varios problemas — rendimiento, múltiples servidores demonio y varios cuellos de botella de arquitectura — y a partir de ahí desarrollé por mi cuenta la arquitectura en Rust.

El primer punto de inflexión fue que el estado residente empezó a limitar el propio flujo de trabajo del agente. Cuando varios agentes consultan a la vez desde distintos worktrees, repositorios y ramas, el modelo de demonio se convierte fácilmente en un problema de coordinación implícita. El segundo fue que cambió mi idea de la frecuencia de consulta: quería algo parecido a una caché L1 / L2 para el agente, capaz de responder en milisegundos antes de cada edición, de cada renombrado, de cada revisión, de cada análisis de impacto. A esa frecuencia, el coste de un demonio en Node.js se vuelve chirriante.

De ahí el juicio central de la arquitectura sin estado en Rust: dejar el grafo en un graph.bin de formato fijo y hacer mmap directo en cada consulta de CLI o MCP. Sin calentamiento, sin estado de demonio y sin depender de que un proceso de vida larga sea de fiar.

Al principio no pretendía rehacer la cola de fusión. Solo quería alimentar la cola existente con las señales de ecp impact, así que hice ecp dev pr-analyze para que el flujo de trabajo etiquetara automáticamente area, risk y cross-pr-conflict.

Pero al usarlo a diario descubrí que lo valioso no era la cola en sí, sino «decidir con el grafo si dos PR pueden convivir sin riesgo». Aunque dos PR toquen archivos distintos, si uno modifica un símbolo dentro del radio de impacto del otro, eso cuenta como conflicto semántico. A la inversa, si están en áreas sin relación y sus conjuntos de impacto no se cruzan, pueden marcarse como de bajo riesgo y sin conflicto entre PR, y dejar que el flujo de trabajo fusione con más soltura.

Lo que esto ahorra de verdad no es el tiempo de una ejecución de CI, sino el ciclo de rebases y reejecuciones que aparece cuando los PR se van desalineando entre sí. La aspiración de ECP aquí es elevar la cola de fusión de «hacer fila por orden de llegada» a «planificar según el riesgo estructural».

No se puede decir que el ritmo con el que los equipos humanos gestionan los cambios sea un error; lo que hace falta es que todo el proceso esté más automatizado para que no frene el desarrollo.

Hoy los agentes escriben código muy rápido, y sin embargo lo que frena es el miedo de las personas: miedo a que el código entre en conflicto, a que el LLM arregle A y rompa B, a los errores de todo tipo. Ese miedo se ha convertido en el mayor obstáculo del desarrollo.

A medida que los proyectos de cada persona, cada equipo y cada empresa crezcan de forma exponencial, herramientas como esta serán más importantes y el rendimiento será la clave decisiva. Lo relativamente importante pasa a ser cómo lograr que el LLM entienda la arquitectura actual más rápido, en lugar de depender del contexto como memoria a largo plazo. La arquitectura hay que dársela a entender a través del código fuente y no de un registro escrito, porque lo único cierto es el código fuente.

En la era de los agentes, el documento más importante pasará a ser el diagrama de flujo, porque lo que una persona tiene que gestionar son los procesos y el diseño de la arquitectura. Con diagramas se capta rápido cada decisión de diseño, mientras que cómo se genera el código, cómo lo verifica una herramienta y cómo lo consume un agente irá perdiendo importancia.

Aun así, los diseños de fondo deben seguir documentándose: cómo aprovechar la caché, si conviene un calentamiento, qué tiempo de espera fijar en el cliente. Esos documentos siguen importando, solo que se abstraen a un alcance mayor. Dicho con precisión, toda la documentación se desplaza hacia un diseño de dimensión más alta.

Igual que hoy escribimos programas sin entrar en cómo se compila o se ejecuta el código máquina. El propio Egent Code Plexus que estoy diseñando no es más que un producto de transición, ajustado a la corriente de este momento.

ECP debe concentrarse en ser una capa de percepción estructural extremadamente rápida, fiable y anclada en el código fuente.

Este proyecto no va a ser —ni necesita ser— otro Codex, Claude Code u OpenClaw. Basta con que sea la herramienta que esos marcos de trabajo, cuando ejecutan flujos con agentes de código, puedan elegir en el momento en que necesitan entender el código. Es un grep y un read pensados para un LLM.

Las herramientas tradicionales responden «¿dónde está esta cadena?» y «¿qué contiene este archivo?». Lo que ECP debe responder es «¿qué es este símbolo?», «¿quién lo llama?», «¿a qué afecta aguas arriba y aguas abajo?», «¿qué riesgo estructural tiene este diff?». El núcleo de ECP no es decidir por el agente, sino entregarle los hechos estructurales que necesita conocer antes de decidir.

La interfaz de producto más importante es la CLI.

MCP da bastante trabajo de mantenimiento, pero como no todos los marcos de agentes de código pueden invocar una CLI de forma nativa, adopté una arquitectura doble en la que MCP encamina hacia la llamada al CLI. Aun así, lo mejor sería poder integrar la herramienta directamente como herramienta de CLI, igual que read. Eso ayuda mucho tanto al rendimiento como al ahorro de tokens.

La ventaja de la CLI es que es simple, barata de mantener, fácil de probar y fácil de meter en CI, y que no arrastra ciclo de vida de servidor, registro de herramientas, compatibilidad de esquemas ni estado de sesión. El valor de MCP es el de una capa de compatibilidad, no el de una abstracción central.

Mientras el LLM no haya interiorizado estos diseños, hacen falta skills que los encuadren y los guíen. Igual que el ser humano, antes de aprender a usar el fuego, no sabía para qué servía; pero una vez que ese conocimiento se extendió, casi nadie ha recibido un curso sobre cómo usar el fuego.

Por ahora siguen haciendo falta esa pauta y esa guía, salvo que algún día el LLM traiga incorporado este tipo de conocimiento. Aun así, prefiero que una skill no sirva para imponer al LLM cómo usar una herramienta, sino para orientarlo. La herramienta describe lo que hace; cómo usarla lo sugiere la skill a grandes rasgos, y cada cual puede ajustarlo a sus necesidades. Lo deseable, claro, es que el LLM lo entienda por sí mismo y lo aplique de forma más amplia.

«Toda acción debe partir de hechos estructurales verificables, no de alucinaciones del contexto.»

Cualquier cosa dicha antes puede ser una alucinación; solo lo que se comprueba en el momento es verificable. De ahí viene la idea de diseñar los peers: alcanzar una interacción casi en tiempo real mediante hooks y peers para evitar que aparezcan conflictos de desarrollo.

Visión

"Todas las acciones deben partir de hechos estructurales verificables, no de alucinaciones de contexto."

En la era de la IA, el cuello de botella es la confianza. Egent Code Plexus asegura que los Agentes siempre regresen a la única verdad: el Código Fuente.


A medida que impulsamos más Agentes y repositorios, lo que importa no es llenar la ventana de contexto, sino tener una herramienta fundacional ultra rápida y consciente de la estructura.
